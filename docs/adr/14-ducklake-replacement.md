# ADR-14 — DuckLake Replaces PyIceberg as the Commit-Path Catalog

**Status:** Accepted
**Decided by:** v3.0.0 scalability rework (base commit `b324e771`; hardened by the `release/v3.0.0` fix series `8fa0dfd1`…`bc495144`)
**Supersedes:** [ADR-01](01-storage-model.md)'s "live-buffer → Iceberg (pyiceberg)" decision, for the commit/durable-store tier only

## Context

ADR-01 fixed the persistence model as live-buffer → Apache Iceberg on Fastly Object Storage, written and read through pyiceberg's `SqlCatalog` (a local SQLite catalog file per process, rehydrated from `metadata.json` pointers discoverable in the bucket itself). That model has a hard ceiling: pyiceberg's SqlCatalog is not safe for concurrent writers, and the manifest-scan-based UI metadata path (`_get_cached_or_scan_metadata`, per-manifest `.avro` fetches through a 16-thread pool) was already showing multi-second cost per scan on a 4-core VM at existing traffic (see the ThreadPoolExecutor-oversubscription comment in `backend/core/iceberg/manifest.py`). Neither property survives a move to horizontally-scaled ingestion (many Celery workers writing concurrently) or the 100k–1M RPS target this rework exists for.

## Decision

DuckDB's **DuckLake** extension replaces pyiceberg as the catalog and write path for the commit tier. Every service attaches its table as `lake` on a DuckDB connection via `_ducklake_attach()` (`backend/core/iceberg/_ducklake.py`); `_commit_buffer_impl()` uses this attach for **every** service regardless of `INGEST_MODE` — DuckLake is not celery-mode-only, it is the storage backend, full stop.

- **Catalog backend is configuration, not code.** `DUCKLAKE_CATALOG` selects a local `.ducklake` file (single-writer, dev/single-pod default) or a Postgres DSN (`postgres:postgresql://...`, required for multi-writer — see [ADR-15](15-multi-writer-topology.md)). The same `_ducklake_attach()` call handles both; nothing downstream branches on which one is active.
- **Tenant isolation is a table-naming contract, not a namespace.** Under a shared Postgres catalog every service attaches the *same* `lake` alias, so a bare `lake.logs` would mix tenants. `ducklake_table_name(source, table_name)` is the single naming authority (`logs_{service_id}`, or `logs_{service_id}__{table_name}` for RUM tables) — every reader and writer (view builder, buffer commit, ingest, admin info) must resolve the table name through it. Never hardcode `lake.logs`.
- **Durability follows the same rule ADR-01 established for pyiceberg**: cloud-backed sources default `DATA_PATH` to `s3://{bucket}/{prefix}/ducklake/` (`_default_data_path`) because raw `.gz` files are deleted post-ingest — a local-disk default would leave the only copy of committed data on ephemeral VM disk. Local-only sources keep a local data path. **Setting `DATA_PATH` is necessary but not sufficient**: it only says where parquet goes *once written*, and inlined rows are never written there until flushed (see the inlining note below). Both halves are required for the guarantee to hold.
- **Size discipline carries over unchanged.** DuckLake's `target_file_size` option is pinned to `LOCAL_COMPACT_MAX_PARTITION_MB` (`_apply_target_file_size`) so `ducklake_merge_adjacent_files` and local tiered compaction never disagree about the file-size ceiling. Many small files remain good for DuckDB scan parallelism; this is not a "merge harder" knob.
- **Small commits land as inlined catalog rows, not files — and only one primitive promotes them.** DuckLake inlines small inserts directly into the metadata catalog (visible as `changes: {'inlined_insert': [...]}` in `ducklake_snapshots`) rather than writing parquet immediately. `ducklake_table_info` therefore legitimately reports `file_count=0` for a table holding real committed rows. Two consequences, both load-bearing:
  - Any code that infers "is there data?" from file count alone is wrong under DuckLake — it must also consult inlined-row state, or count rows directly.
  - **`ducklake_flush_inlined_data` is the ONLY primitive that promotes inlined rows to parquet.** Neither `ducklake_merge_adjacent_files` nor `ducklake_rewrite_data_files` does — both operate on already-materialized files, so a table whose every commit was inlined stays at `file_count = 0` forever no matter how often compaction runs (verified empirically on a throwaway catalog, and observed live: 27,613 committed files, 27,615 catalog snapshots, **zero** bytes in the FOS `ducklake/` prefix). Combined with the durability rule below — the pipeline deletes raw `.gz` after commit — an unflushed catalog means the only copy of the data is the catalog itself. The flush must run on the compaction tick, before raw deletion in the same cycle. This was a live bug on this branch, fixed by adding the flush to `merge_lake_files()`; the durability guarantee below is only real because of it.

## What did NOT move to DuckLake

`backend/core/iceberg/buffer.py` and `backend/core/iceberg/sync.py` still call pyiceberg's `catalog.load_table` / `_table_identifier` / `_get_catalog` extensively. Whether that's still load-bearing or a leftover of an incomplete migration is an open question this ADR does not resolve — it is scoped to the commit-path/catalog decision only.

What is confirmed broken by the cutover: any reader still built on pyiceberg's Table API (`table.snapshots()`, `table.current_snapshot()`, manifest scanning) now reads a catalog that receives zero new commits. It doesn't error — it silently reports empty or frozen-at-migration-time state forever. `backend/core/iceberg/manifest.py::get_table_info`/`get_snapshot_calendar`, the post-commit `table_summary.json` writer in `_core.py`, and `lake_info.py`'s pyiceberg fallback were all found in this state and rewritten against DuckLake's SQL introspection functions (`ducklake_table_info`, `ducklake_snapshots`, `ducklake_list_files`) — see the `release/v3.0.0` commit that lands alongside this ADR for the exact query shapes. **Lesson for future migrations**: a catalog swap that changes the write path but leaves old readers pointed at the old catalog fails silent, not loud — audit every caller of the old catalog's read API before considering a cutover done, not just the write path.

## Consequences

- `config.validate_ingest_mode()` hard-fails backend/worker boot when `INGEST_MODE=celery` is paired with a non-Postgres `DUCKLAKE_CATALOG` — a file catalog cannot serve concurrent worker writers plus backend readers without torn merges (observed as `404 NoSuchKey` on reads during testing). This makes the single-writer constraint a boot-time gate, not a runtime surprise.
- Admin/analyst "table info" and calendar panels must be read as DuckLake-native queries against `ducklake_table_name(source, table_name)`, never as pyiceberg Table objects, from this point forward.
- **Under a shared Postgres `DUCKLAKE_CATALOG`, the DuckLake snapshot log is catalog-GLOBAL, so snapshot retention and file cleanup cannot be per-tenant.** This is a property of the catalog choice, not a bug in a caller, which is why it belongs here rather than in the function docstring where it previously lived alone (`backend/core/iceberg/buffer.py:863-865`). Concretely: `_ducklake_expire_snapshots` derives `cutoff` from ONE service's `cron_sync.keep_snapshot_days` (`buffer.py:869`, resolved at `buffer.py:1023`) and then calls `ducklake_expire_snapshots('lake', older_than => cutoff)` (`buffer.py:883`) and `ducklake_cleanup_old_files('lake', older_than => cutoff)` (`buffer.py:913`) against the whole catalog. A tenant configured with `keep_snapshot_days=1` therefore destroys a co-tenant's 30-day time-travel window and physically unlinks their parquet — and because the weekly `expire_{id}` job is registered per service, whichever service runs last wins. The `snapshots_before`/`snapshots_after` counts reported back are likewise fleet-wide, so the per-service cron result is not attributable to that service. Multi-tenant deployments must either keep `keep_snapshot_days` uniform across every service sharing a catalog, or give each tenant its own catalog. Neither is currently enforced in code.
- ADR-01's live-buffer tier and rollup-as-query-optimization decisions are unchanged and still in force. Only the durable-store implementation moved.

## Out of scope

- Removing pyiceberg from `buffer.py`/`sync.py` (separate task, needs its own audit of whether those code paths are still reachable).
- A full DuckLake-vs-Iceberg-table-format-v3 comparison — DuckLake was chosen for its multi-writer transactional catalog, not evaluated against every alternative.
